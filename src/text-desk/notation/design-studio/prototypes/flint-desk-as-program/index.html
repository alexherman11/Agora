No proposed notation. Every card, chip and trail below is real state from explore.py proto-flint --dump and a real transcript. Click a card to see how it got there.

The program (7 rules, 3 scripts)

  
# state drives position
r1 when prop:state=doing  do move into=Doing
r2 when prop:state=review do move into=Review
r3 when prop:state=done   do move into=Done
# a condition that works
r4 when in:Doing,prop:size=5 do tag add=too-big
# the button: a tag is a click
r5 on tag by=flint do run start $item
# the clock
r7 when kind:task,due<2026-09-19,-prop:state=done
                        do tag add=overdue

script start  = do prop $1 state=doing ; do prop $1 owner=flint
script finish = do prop $1 state=done  ; do tag  $1 add=closed
script report = do comment $1 line="size is $1.size ..."  ← does not expand






  
One command, three rules deep

  
> do tag a11 add=go
ok tag a11 add=go  [e18]
  tags now: design,go
~ r5 fired on a11: run start a11
       → ok prop a11 state=doing  [e19]
~ r1 fired on a11: ok move a11 into=f03  [e21]
~ r4 fired on a11: ok tag a11 add=too-big  [e22]

  
This is the finding. A tag is a button, a rule on a verb is
  an event handler, and rules chain — so the desk is already programmable, and every step of the
  program prints itself, attributed and undoable as one act. Nothing was added to make this work.







Where it broke


    
  
  • Silent argument drop. do create … props=state:inbox,size:5 wibble=7
  returns ok and echoes every argument back — and applies none of them.
  props is not a create argument at all. The now: line is
  honest; the ok line repeats what was typed, not what was done,
  and a reader cannot tell them apart. The three dashed chips below are props I believed I had set.
    • 
  
  • $item fired on the wrong object.
  rule on tag by=flint do tag $item add=looped, triggered by an event on
  a07, tagged a14 — the session's last-created thing.
  $item means two different things in help rules and
  help handles, and the handle wins. Select "Silent argument test" to see
  why record a contradiction in one line.
    • 
  
  • No count, so no WIP limit.
  rule when in:Doing,count>3 … → unknown selection term. A view can display
  "3 matches"; nothing can act on the 3.
    • 
  
  • No numeric comparison on props. prop:size>3 is refused;
  only due< and age> compare.
    • 
  
  • Scripts cannot read a value. $1.title exists;
  $1.size substitutes the literal text a11.size.
  Scripts pass ids and literals, and compute nothing.
    • 
  
  • The help and the parser disagree. find prop:owner is refused by an
  error message that states the rule it is refusing: "prop:k alone selects things that have k".
