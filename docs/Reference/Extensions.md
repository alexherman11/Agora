# Extensions

Extensions let useful behavior emerge from ordinary work. The current native
package system retains source, build and installation identities and exposes
installed actions and skill files. [[Runtime Guide]] contains the implemented
manifest and invocation formats.

## Reuse without ceremony

Look for a suitable installed capability when discovery is likely to help. A
brief search is often enough. Personal experiments do not need exhaustive registry
research, numerical reuse thresholds or a formal rationale for every small type.
Record non-obvious compatibility choices; demand more evidence when many people
will depend on a shared contract.

Use data and presentation edits for behavior already expressed by an installed
capability. Author executable code for new behavior. A compact common interface
can coexist with specialized actions and new operation families. Package lifecycle
steps are implementation mechanics, not mandatory prompts in the human workflow.

## What a package exposes

Actions describe their supported input and useful output. Native human controls
and JEFF tools share action meaning and current authorization, without requiring
an identical UI projection. Tools remain available when a view closes. Generic
inspection and export can make a new schema useful before a custom view or file
format exists. Domain formats and richer projections can follow actual need.

An action may combine reading, computation, observations and writes. Describe
relevant effects and lifecycle boundaries rather than assigning every application
to one exclusive class. Pure evaluation excludes hidden external effects; broader
actions can perform authorized I/O. Repeatability and deduplication depend on the
actual protocol, operation identity and payload, not on having a receipt alone.

## Evidence and adoption

The current runtime uses explicit source/build/install operations and a separate
yard for candidate Python execution. A failed required check is not a pass. The
appropriate checks depend on whether this is an isolated preview, a personal
experiment or a stable shared package. Do not move untrusted candidate execution
into the credentialed guest as a fallback for a missing isolation boundary.

Standing delegation can cover editing, testing and activation. A one-effect
approval and an ongoing development grant are different things. Neither source
content nor a package's own assertion expands current authority.

Owners may pin a version, review offered updates or select automatic compatible
adoption. Live theme data and template inheritance need not follow the same
policy as executable code or migrations. Preserve implementation identity and a
recoverable path when behavior changes. Full dependency locking and generalized
package migration are not implemented by describing them here.

## Compatibility and shared vocabulary

Prefer understandable names and compatible meanings. Local vocabularies can
evolve into shared ones when reuse justifies the work. Technical standardization
is ordinary engineering; it need not require constitutional promotion. Rights or
authority changes are a separate concern.

Unknown inert data should not be lost merely because a view does not understand
it. Relevant unsupported action semantics may require refusal. A generic versioned
export envelope can carry schema/source references and retained bytes before
specialized file forms are useful. The present schema-admission behavior is
narrower than this longer-term compatibility direction.

## Useful experiments

Build a small native editor. Reuse its selection and document actions in another
view. Add a capability not anticipated by its original author. Measure what must
be rewritten, how much source is retransmitted and whether a smaller agent can
use the installed contract without reading implementation. These are evidence
questions, not universal gates for every small change.
