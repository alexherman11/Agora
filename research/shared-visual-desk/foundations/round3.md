# Foundations round 3: authored programs over a designed world

2026-09-18. Author: foundations, Astra team. This is a bounded research interpreter and an integration contract for Editing's browser workbench. It is not a deployed Agora capability or a general replacement for the existing text desk or Tessera. Earlier findings and round-two artifacts remain unchanged.

The concrete result is `program.mjs`: a JSON AST can select objects by semantic fields, compute local values, branch, and propose several edits. The same AST is intended for source and visual authoring. Twenty focused Node tests pass. Browser input, visual quality, persistence through the actual interface, and authoring usability are separate evidence owned by the coordinator and Media; this report does not infer those results from the module tests.

## What runs

`PROGRAM.md` specifies the exact current API and grammar. Programs contain event-selected rules, expressions, and four step forms: `let`, `set`, `if`, `forEach`. Expression calls are JSON arrays. No program-supplied JavaScript, eval, host imports, timer, network or DOM operation is executed. This interprets data under hard limits; it is not a hardened sandbox for arbitrary JavaScript callers.

A useful tested example selects only items whose role is signal, multiplies each selected item's value by three for its size, branches on that value to choose its fill, and composes a separately authored caption rule. Preview returns changed addresses, old/new values, contributing rule IDs and AST origins. It leaves the supplied state untouched. Application yields a fresh state and a live undo receipt.

Every rule reads the same input snapshot. Local lets are sequential; proposed state writes do not become inputs to later steps. Disjoint changes compose. Identical writes coalesce while retaining contributor identities. Different writes to the same address, and parent/child overlaps, refuse the entire preview. This makes one particular policy inspectable; it does not prove that this policy suits every application. A procedural drawing program may deliberately want ordered writes. A maintained constraint network needs scheduling and dependency semantics absent here.

The evaluator does not silently manufacture fields when a path is wrong. JSON state can contain arbitrary added objects, but the fields being set must already exist. This makes typos visible at the cost of needing another authoring operation to create the object's shape. Creation/deletion was not added to the grammar merely because the desired interface became a spatial world.

## Spatial worlds expose a policy question, not automatically a missing opcode

The final two tests respond to the user's chosen direction, a playful, spatial, highly customizable world. One appends a previously absent object with id, role, position and style, then selects it by `controls.activeId` in a `forEach`. A drag event writes clamped x/y from control inputs. Existing objects retain their values. The evaluator therefore can address newly authored objects without one hard-coded rule per object.

That test has no pointer input or renderer. Its role is to distinguish a representational obstacle from an interaction-policy obstacle. When a positioning rule and a human drag both concern the same object, an instrument still must define what a drag means: edit the rule's input, edit its rest position, suspend that rule, or create an override. Adding a `drag` language primitive would hide this choice unless its contract made the same decision explicit. Stable semantic IDs are useful for selection, but duplicate IDs and object schema are currently domain responsibilities.

A next discriminating interaction should begin with an independently authored arrangement rule, then let the person drag one affected object. Show the prior rule and the proposed change to its input or override; check that an agent can explain the same resulting behavior from the program and receipt. Success would support the shared-program approach. Needing uninspectable widget-local exceptions would count against it. The existing tests do not establish that result.

## Three failure boundaries

1. **Definition admission:** malformed operators, arity, paths, unsafe keys and duplicate rule IDs are rejected even inside inactive events and branches. Domain bindings and types need additional domain validation. A draft editor should preserve the invalid draft while retaining the previous working installed program.
2. **Evaluation admission:** a syntactically valid program can encounter a missing object, zero denominator, conflicting conditional writes or a data-sized execution budget failure later. Gather and validate local effects before applying any of them. This is refusal before effect, not an attempt to reverse an external action already performed.
3. **User compensation:** a successfully accepted local edit can be undone using its retained receipt if the supplied state still matches the recorded resulting values. This is a separate operation, not the mechanism used to recover from failed preview.

The final test first evaluates a valid division rule successfully, then changes its denominator to zero, then removes the referenced field. Both later previews return inspectable errors and no changes; an earlier proposed title change remains unapplied. The program object remains intact. This tests future-data failure, not merely an invalid definition at creation time.

Apply and undo use conservative whole-state value fingerprints. They refuse after any unequal intervening state, including unrelated edits. They cannot detect an ABA sequence that returns to identical values. Handles are private, ephemeral and single-use; they cannot be copied through JSON and re-admitted. This is adequate for an isolated workbench experiment, not a collaborative history protocol. Public preview row edits cannot change the retained writes, but this does not establish security against hostile code in the same JavaScript host.

## Existing work and primary reading

I read the current local text-desk script and rule implementation in `research/text-desk-lab/notation/desk_knife.py`, around lines 566-710, and the relevant command dispatch. Named scripts substitute arguments into command strings and dispatch them. Rules track matches and can run subsequent bounded rounds. A rule-capable command dispatcher also means a script can author a rule; a string template is not proof of a lack of metaprogramming. I did not execute private sessions to establish this.

I also read `research/tessera-lab/LANGUAGE.md` and the effect/expression sections of `engine.mjs`, around lines 200-280. Tessera already explores contributed relations, same-snapshot composed effects, conflict refusal and pure expressions. This round deliberately borrows that policy. Its narrower contribution is a portable small AST with explicit preview rows, runtime diagnostics and a browser-authoring boundary. It lacks Tessera's broader composition machinery and does not supersede it. A concrete policy difference: this evaluator rejects division by zero; the inspected Tessera expression implementation returns zero. These are choices to test, not a reason to declare one universally correct.

Primary-source coverage is explicit:

It distinguishes structure, values and picture, and describes applying tools to targets. It also separates the original system from the reproduction and notes input limitations. I did not read the entire ThingLab thesis this round. My inference: a shared underlying structure does not alone settle the behavior of a gesture or the feedback needed to make it intelligible.
- [Myers et al., Garnet: Comprehensive Support for Graphical, Highly Interactive User Interfaces](https://www.cs.cmu.edu/~garnet/garnetIEEE.pdf): partial reading, not all 15 pages. Read introduction/object-system sections at printed pages 71-74; constraints discussion at 74-75; interactors/input protocols at 78-80; debugging and C32 passages at 81-84. The paper separates graphics from interaction protocols, discusses one-way constraints and their runtime costs, and presents inspection of values/formulas. Its reported implementation status distinguishes completed tools from work underway. It also notes that dynamic slots can turn misspellings into unintended properties. My inference: our existing-path refusal is a useful contrasting policy to test, while visual authoring needs runtime inspection rather than only prettier source entry. This is not evidence that our four-step interpreter reproduces Garnet.
- [diSessa and Abelson, Boxer: A Reconstructible Computational Medium](https://boxer-project.github.io/boxer-literature/papers/Boxer,%20A%20Reconstructible%20Computational%20Medium%20(diSessa%20&%20Abelson,%201986).pdf): reused the complete ten-page extracted-text reading recorded in round one; did not newly reread all pages. The relevant earlier argument is that tools themselves must remain reconstructible, and alternate representations should remain attached to the same computational material. This motivates testing whether the visual editor preserves source it cannot yet express.
- [Maloney and Smith, Directness and Liveness in Morphic](https://worrydream.com/refs/Maloney_1995_-_Directness_and_Liveness_in_Morphic.pdf): reused the complete eight-page reading recorded in round one. This round does not claim a new complete rereading. Direct live objects remain a serious rival: their immediate graphical manipulation and inspectable behavior may offer a better inhabited experience than explicit preview/application for every small action.

No novelty claim is made for ASTs, bounded interpretation, direct manipulation, constraint programming or visual formula editors. The experiment asks which boundary lets rich authored appearances and agent-readable manipulation coexist without flattening their meaning.

Root relayed Claude researchers Moss and Wren's reports on studio a336: scripts installed rules, exported state omitted firing/cause history, an invalid target was accepted until firing, and one invalid style input preserved prior DOM. These are attributed reports, not our independently repeated trials. My reply is Dispatches a112, event e95. Definition validation and atomic runtime effects are complementary. A statically admitted rule can fail on later data. Retaining a prior authored program, retaining an editable invalid draft, refusing partial effects, and undoing a successful change are distinct requirements. I revise any broader suggestion that the current scripts cannot author behavior. The concrete disagreement is whether definition-time validation alone addresses later data failure; our new test supplies a counterexample.

## Read-only persistence review

At the coordinator's request I reviewed `workbench_server.py` and its tests without editing them. The store holds the same visual-desk guard used by the text launcher, compares a subject/revision token, rewrites through desk dispatch, and atomically replaces its pickle file. This is a credible local CAS boundary. Validation there checks document shape/size, not evaluator syntax or renderer schema. Lost-response retries with an old base can conflict even if the first save succeeded; there is no idempotency receipt. Flushing a temporary file then replacing it is not a tested power-loss guarantee. Corrupt state or lock timeouts can escape structured HTTP error responses. These observations were sent to root; they are source review, not a new fault-injection result or browser result.

The module bounds operations to 8,192, proposed writes to 256, loop iterations to 512, JSON depth to 24, input nodes to 20,000, strings to 16,384 characters and rules to 32. Callers may lower three execution budgets. There is no recursive user call, unbounded loop, maintained dependency graph, domain schema, persistent receipt, general undo/redo, object lifecycle, distributed concurrency or authority model. Complex software cannot yet be reduced to this fixture without inventing missing capabilities. What is now concrete is a small useful multi-step program, its shared representation and its inspectable failure boundaries, ready for the separate human interaction test.
