## 3. Design conclusions from the workshopping (imagined unless said)

These are what I argued and where Alex pushed back. He agreed with the thinking; nothing is decided.

### 3.1 The store and versions (a1960, read; the rest imagined)
- Today the truth is a snapshot (the pickle); the event list exists for undo. For many people and merging, **the log must be the truth and state derived**.
- Order I proposed: (1) measure the 124 MB and move desk state (seen, views, per-reader positions) out of the world file, per person; (2) **append-only JSONL event log** as truth, `replay` rebuilds a world, health checks each frozen world replays to its snapshot; (3) plain JSON snapshot written occasionally (the goldens already load this way); (4) **global thing ids with per-world handles** (the hard one); (5) merge on the log. Alex: "hold that for now but I like your thinking."
- Alex's correction, which I accept: **refusing and naming is a floor, not a way to update an app; things must work, not break halfway.**

### 3.2 Packets, not merges
- A change travels as a **packet**: definitions (lens, roles it adds to a style, verbs, kinds, help) plus the commands that place them, with **needs computed** from the lens compiler's resolve stage and **satisfied, not checked** (a lens that needs a role ships the role).
- Taking a packet is a **trial on a fork, then one step**: applied as one `install` event, undone whole; otherwise nothing moved and the report says what it would add and what it cannot satisfy.
- **Drift is handled by living beside, not three-way merging**: additive packets never conflict; a changed shared lens arrives beside yours with the same origin; re-expressing your changes is tried on a fork; true merging is for leaders landing variants, with a person present.
- A packet that needs newer host code means "this update also updates your desk" (the door routes persons to code versions already).
- We already have most of a packet: `worktree diff` prints a fork's journal as commands and `merge` replays it all or nothing with ids remapped.

### 3.3 Modules and the painter
- Alex's question: do we need JavaScript? Could modules replace lens.js? Native rendering? Our own language?
- Three questions that JS answers at once: what people write, what runs it, what medium shows it. **The lens language stays the one language people write.** At the edge (globe, map, chart, sim) a **module** fills one part.
- Runtime: fenced **JavaScript first** (iframe/realm, capability API, watchdog), because the libraries for the 3D earth are JS; **WebAssembly** is the path to native and to budgets (fuel) and the same bytes on every medium. The **contract**, not the language, is the design: a module declares what it draws, what the text printer says for it (print never behind paint), and is deterministic over its inputs (pixel goldens).
- A **bounded drawing language of our own** is worth a prototype as the first module language (pins, charts, badges), not a general-purpose language.
- Away from lens.js entirely: one painter in Rust to wasm and native is possible; **not first**, because the DOM gives text layout, selection, input methods, accessibility. Hybrid: lens.js stays the browser painter of the base words, modules take canvas/WebGPU/wasm inside a part, native painters per medium under the same scene contract.

### 3.4 Three levels, two dictionaries, one new kind (Alex asked to scrap a level)
- **Three levels: things, lens, painter.** Style is not a level: it is the painter's dictionary of looks (role → tokens). Modules are not a level: the painter's dictionary of words, living in the world.
- **Rule: a lens never paints, a module never selects.** A module as lens-plus-painter would be a second reader of the world with no fence; the lens gathers (`earth : module globe, of kind:pin, each pin`), the module paints the subtree, a touch raises "pick this item" so the lens's `on click` fires.
- Floor is three: killing the scene (world-as-DOM with style selectors, or lenses emitting pixels) loses the text printer and the meaning of gestures.
- **The window manager is a lens over a thing we don't have: the `sitting`**, a per-person thing holding which lens anchors, what fills each slot (`lens $sitting.right`), folds, sizes dragged, focus, history. In code once, as painter base words: split panes, resize handles, focus, z-order, keyboard routing, local drag with commit on drop. In data: the policy (anchors hold, satellites navigate, collapse the left when the right fills, which is `only when $sitting.right`). Outside both: a **boot surface** that is never a lens (Wren's rule: a shell that is entirely a lens cannot report that lenses are broken).
- Sitting state must **not** be world events (every scroll an event is wrong): it wants the per-person observation store (Sable's c1963), same shape, frozen and replayed.
- Alex: "I'd rather it work well." Build the frame words once, well, in code; let the policy be data.

### 3.5 Views, composition, OpenDoc (Alex's five questions from his other coding agent)
1. **Driven from outside?** Yes: a view is a function of the world and the viewer; others drive it by changing what it reads. Gap: viewer state has no home (the sitting).
2. **A mediator between views?** Yes, fully: the desk; every gesture is a command through the door; policy is lens words.
3. **Freeze/thaw?** Half: scenes are reproducible from lens id/rev, world @N, viewer; fold/scroll have no durable home (the sitting fixes it).
4. **Declared capabilities?** Kinds make it possible: `shows=kind:url` on a lens, `holds=kind:task` on a room; nothing reads them yet.
5. **Layout made about views?** Yes; the exception `at item` is the world's geometry, not the view's. The shell frame (sidebar, window frame in lens.html) is still code, so a slide cannot push it.
- **View contract**: *shows*, *gives* (gestures, which are desk commands), *needs* (roles, verbs, kinds, host version), *says* (text form). Everything on screen is a part of a scene, produced by a lens or a module under one part contract.

### 3.7 Lens vs module, slowly (for Alex's question)

The lens never says a colour, size, font or pixel, and cannot.

## 10. Added later on 7 Oct: live editing, the painter as words, layers and anchors

### 10.1 What is live today, and where it strains (read and ran)
- **World edits** (lenses, styles, verbs, rules, kinds, help) are live by construction: an event, the door's stream, a repaint. A lens that stops compiling shows its last good version with a `!` line and gestures off; a gesture carries what the person saw and is refused if the thing moved under it; `undo` takes anything back. This is the designed way to change what someone sees while they use it.
- **Python edits** go live by the door swapping deskd when HEAD moves and health passes (a1505); the old one finishes its calls; nothing reloads. Workers land through the workshop (own git worktree, merge `--no-ff`, health, revert on failure; the keeper reverts a landing if the house dies three times after it). Agents must never edit the main checkout: uncommitted edits there block every landing (Sable's stall of 1 Oct).
- **Painter edits** (`desk-shell/*`) are live **immediately** since 27787f6 (Alex, 7 Oct: "at least for now"): deskd hashes the static files on disk on every `/api/version` (committed or not), the page sees a new hash within five seconds and reloads itself keeping the view, drafts, terminal and caret, unless something is carried, held or being typed, when it says it is waiting and tries at the next tick. Until then the quiet line offered a click and the person chose (Juniper e3746). Logged as friction **a3401**: when the screen takes new code is a policy living in lens.js.
- Strains: everyone moves to new code together (no per-person routing yet, a1654); a painter change reloads the whole page; the swap reloads a 124 MB pickle; a coding agent cannot see the picture (the Codex testers are the eyes).
- Alex's question answered: yes, a coding agent may edit the visualization while he uses it. A lens edit shows on the next repaint; a painter edit reloads when his hands are free; a Python edit swaps after health. Modules with inner state will need freeze/thaw in their contract so a swap keeps his place.

### 10.2 Per-part reload and the shell lens are one idea (imagined)
- Data already reloads per part: the painter keeps every element and remakes only parts whose paint, acts or kids changed (the signature in `make`), carrying folds, scroll and drafts. Code reloads per page because lens.js is one interpreter and the unit of code is the file.
- **The painter's words as modules.** lens.js is 430 lines and its body is word-sized functions: `make`'s per-act branch, `frames` (gap, scroll, measure, fold), `tracks`, `edits`, `runs`/`source`, `drags`, `carries`/`take`/`put`/`ghost`, the menu, `semantic`. Each can be a note of a kind `word` with a contract: the paint keys it answers to, what it needs from the host (rectangle, subtree, style tokens, viewer state for its parts), what the text printer says for its parts, deterministic over inputs (pixel goldens). The host that remains is the loop (`refresh`, `paintAnswer`, the first lines of `make`, continuity), the boot surface, and the trust gate (only words the person took run; signed by maker). "The word changed" then remakes only the parts that use it, from the scene and the sitting; the signature gains the word's version. State must leave the DOM for the sitting first.
- **The shell as a lens over the sitting** makes the top of the page a scene: slots (`lens $sitting.left|main|right|line`), a few frame words in code (split, resize handle, focus, z-order, keyboard routing, local drag with commit on drop), the terminal and the quiet line as words painted into slots. The reload policy I hard-coded becomes a lens line. What stays a page reload: the loop and the boot surface.
- **Order proposed:** sitting as a thing and viewer state held per part in it → the loop extracted from lens.js with today's functions registered as words by name (still in the file; nothing changes for anyone) → words moved out one at a time, terminal and quiet line first, fold and menu next → the module slot for foreign code falls out.
